   106: ## 4. Endpoint-only vs full-window session constancy
   107: 
   108: ### 4.1 Exact wording
   109: 
   110: v3.4 §5.2 (a), verbatim:
   111: 
   112:   session_key[t+h] == session_key[t]
   113: 
   114: v3.6.2 §6 (k), verbatim:
   115: 
   116:   For every k in [0, h]:
   117:       session_key[t+k] == session_key[t].
   118: 
   119: Both rules use session_key as a function of the bar index. Neither
   120: specification defines session_key. The working definition in the
   121: project (from prior audits) is: session_key = begin.dt.date, with
   122: weekend shifts as implemented in main.trading_session_key.
   123: 
   124: ### 4.2 Abstract example where the two rules diverge
   125: 
   126: Consider a sequence of session keys over bars 0..8:
   127: 
   128:   [S1, S1, S2, S1, S1, S1, S1, S1, S1]
   129: 
   130: i.e., bars 0-1 are S1, bar 2 is S2, bars 3-8 are S1.
   131: 
   132: Take t = 0, h = 6.
   133: 
   134:   session_key[t]   = session_key[0] = S1
   135:   session_key[t+h] = session_key[6] = S1
   136: 
   137:   v3.4 (a): S1 == S1 → True. Bar 0 is admissible by this rule.
   138: 
   139:   v3.6.2 (k): check every k in [0, 6]:
   140:     k=0: S1 == S1  True
   141:     k=1: S1 == S1  True
   142:     k=2: S2 != S1  False → rule fails.
   143: 
   144:   v3.6.2 (k): False. Bar 0 is not admissible.
   145: 
   146: So the two rules differ whenever:
   147: 
   148:   - session_key at the two endpoints t and t+h matches, AND
   149:   - at least one interior bar has a different session_key.
   150: 
   151: Such a configuration can arise in principle if sessions interleave
   152: inside the forward window (e.g., crossed sessions, short sessions).
   153: 
   154: ### 4.3 Effect on eligibility
   155: 
   156: Under all other conditions being equal, v3.6.2 (k) is strictly
   157: stricter than v3.4 (a). v3.6.2 excludes bars that v3.4 admits when
   158: the endpoints match but an interior bar does not.
   159: 
   160: ### 4.4 Direct textual verification
   161: 
   162: Confirmed by text: the two rules are not equivalent in wording.
   163: 
   164: Not confirmed by text alone: how many bars are affected on the four
   165: audited datasets. This cannot be answered from the specifications
   166: and requires a read-only audit on the datasets and horizons.
   167: 
   168: Open item: the definition of session_key. If session_key is

   170: audited data (they end the same calendar day), then interleaving of
   171: the form S1, S2, S1 inside [t, t+h] is unlikely but not proven

    25: ## 1. Problem statement
    26: 
    27: The H4 specifications v3.4 and v3.6.2 both use the quantity
    28: `range_atr`. Neither specification defines it.
    29: 
    30: Specifically:
    31: 
    32:   - v3.4 §2: event is `range_atr[t] < q25(range_atr) = +0.54835695`.
    33:   - v3.4 §5.2 (g): eligibility requires `range_atr[t] is finite`.
    34:   - v3.6.2 §2: event is `Event_tag(t) := range_atr[t] < 0.54835695`.
    35:   - v3.6.2 §6 (e): eligibility requires `range_atr[t] is finite`.
    36: 
    37: No formula for `range_atr` appears in either specification. No
    38: definition of `atr14` appears in either specification. No rule for
    39: the case `atr14[t] == 0` appears in either specification. No rule
    40: for session boundaries appears in either specification.
    41: 
    42: Consequently, the currently frozen threshold `0.54835695` is a
    43: number whose inputs are not fully specified by the H4 documents.

   136: ## 3. Proposed definition for H4
   137: 
   138: The following definition is proposed. It is NOT adopted by this
   139: document. It requires explicit user authorization.
   140: 
   141: ### 3.1 range_atr
   142: 
   143: For each 5M bar t:
   144: 
   145:   range_atr[t] = (high[t] - low[t]) / atr14[t]
   146: 
   147: provided atr14[t] is finite and atr14[t] > 0. Otherwise:
   148: 
   149:   range_atr[t] = NaN
   150: 
   151: ### 3.2 atr14
   152: 
   153: atr14[t] is computed by the formula found in
   154: main_v5.17_threshold_path_lab_v2.calculate_indicators:
   155: 
   156:   previous_close = close.shift(1)   # across the whole dataframe,
   157:                                     # no reset at session boundaries
   158:   tr1 = high - low
   159:   tr2 = abs(high - previous_close)
   160:   tr3 = abs(low  - previous_close)
   161:   true_range = max(tr1, tr2, tr3)
   162:   atr14 = true_range.ewm(
   163:       alpha = 1/14,
   164:       adjust = False,
   165:       min_periods = 14,
   166:   ).mean()
   167: 
   168: Notes on the formula:
   169: 
   170:   - Smoothing is Wilder EWM (RMA), not a simple rolling mean.
   171:   - adjust=False means the recursive EMA form is used.
   172:   - min_periods=14 means the first 13 values are NaN.
   173:   - previous_close uses close.shift(1) without session reset, so on
   174:     the first bar of a session after a break, previous_close is the
   175:     close of the last bar of the previous session. This can produce
   176:     larger true_range at the first bar of a session. This is a
   177:     property of the existing code, not a defect.
   178: 
   179: ### 3.3 Consequences if the proposal is adopted
   180: 
   181: If adopted:
   182: 
   183:   - range_atr is NaN whenever atr14 is zero, negative, or NaN.
   184:   - The H4 event condition `range_atr[t] < 0.54835695` is False
   185:     whenever range_atr[t] is NaN (comparison with NaN is False).
   186:   - The H4 eligibility conditions §5.2 (g) / §6 (e), which require
   187:     `range_atr[t] is finite`, exclude NaN range_atr values.
   188:   - No bar is affected by the choice between F1 and F2, because F1
   189:     and F2 produce identical values on real data.
   190: 
   191: No sample count, no eligibility-set count, and no numeric
   192: consequence is computed in this proposal.
